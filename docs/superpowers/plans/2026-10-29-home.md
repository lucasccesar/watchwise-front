# Home Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build the authenticated Watchwise Home from the local responsive prototypes and design system, using the documented home-summary API.

**Architecture:** Add an in-memory session service and route guard for `/home`; keep the public layout for account routes and mount Home under an authenticated responsive shell. A feature-local API service types the summary response, and the standalone Home page renders its sections directly from that single summary response.

**Tech Stack:** Angular standalone components, Router, Signals, HttpClient, RxJS, semantic design tokens in `src/styles.css`.

## Global Constraints

- Use relative API URLs under `/api/v1` and preserve cookies and CSRF configuration.
- Use the local `telas-reqs-definitivo.md` contract and prototype breakpoints; do not call TMDB or create demo content.
- Keep authenticated user data in memory only; never store tokens in browser storage.
- Preserve loading, empty, and API error states in Portuguese.
- Keep the “mark as watched” action unavailable while the API CSRF cookie path prevents Angular from reading its token.
- Do not modify `angular.json` or the separate API repository.
- Do not add or run tests unless requested; run the existing build for compilation verification.
- Keep the implementation in one reviewable Home unit and make no intermediate commits.

**Interfaces:**
- `AuthSessionService.setUser(user: AuthenticatedUser): void` stores the login result in memory.
- `AuthSessionService.ensureUser(): Observable<AuthenticatedUser | null>` loads `/users/me` if needed, retries once through `/auth/refresh` after 401, and never reads or stores cookies.
- `HomeApiService.getHomeSummary(userId: string): Observable<HomeSummary>` calls `GET /api/v1/users/{userId}/summary/home` once on page entry.
- `HomeSummary` mirrors the local contract for totals, viewer, notifications, next episodes, upcoming releases, 30-day counts, recently watched, and social activities, including required `distinctSeriesWatched`.

**Contract differences recorded before integration:** the local snapshot names the upcoming-event date `releaseDate`, while the checked-in API implementation serializes `CalendarEventDTO.date`. Use `date` because it is the confirmed API property and request that the API contract snapshot be reconciled. `distinctSeriesWatched` is present in the local requirements snapshot and is required by the page.
